# 反模式与禁忌清单

> 使用本 Skill 时常见的错误做法，以及 AI Agent 应当避免的行为。
> 在技术选型、架构设计、需求分析或持续开发时加载本文档对照自检。

## 核心原则

**美化措辞不等于实质改进。** 本 Skill 的价值在于强制结构化的工程流程，任何"跳过流程、直接给结论"的做法都是对 Skill 的误用，即便结论本身正确。

---

## 七大反模式（错误 → 正确对比）

> 注：原七大反模式之外，根据 SkillHub TRACE 评测反馈，新增 8、9 两条针对"国内场景"与"规模切换"的高频误用。

### 反模式 1：一句话需求直接糊代码

```
❌ 错误：
用户："我要做一个商城"
AI：直接生成 Vue + SpringBoot + MySQL 完整项目

✅ 正确：
1. 确认用户类型 → 进入对应模式
2. 判定规模级别（S/M/L）与项目类型（全栈/纯前端/纯后端）
3. 需求分析：拆解业务层 → 领域模型层 → 应用服务层 → 技术层
4. 逐层交互式选型，每轮重新动态调研
5. 输出领域模型草图与技术栈汇总，用户确认后再初始化
```

### 反模式 2：选型阶段一次性抛出所有问题

```
❌ 错误：一次性用表格列出 12 个前端层级 + 8 个后端层级让用户挑选

✅ 正确：每轮只通过 ask_followup_question 询问一个层级，
        用户确认后重新 web_search，再生成下一轮候选
```

### 反模式 3：AI 代替用户做技术决策

```
❌ 错误：用户说"做个管理系统"，AI 直接锁定 Vue + Element Plus + Pinia

✅ 正确：每个层级都给出候选（标注"推荐"+理由），由用户勾选确认；
        即使框架生态只有一个主流方案，也不得自动锁定
```

### 反模式 4：推荐写死的过时版本号

```
❌ 错误：推荐 "Vue 3.2"、"NestJS 9" 等固定版本

✅ 正确：按 0.1 协议实时查询最新稳定版本（npm view / Maven Central / PyPI），
        运行时一律选当前 LTS，禁止沿用文档表格里的历史版本
```

### 反模式 5：大项目套小架构 / 小项目套大架构

```
❌ 错误 1：脚本工具也强制生成 .agent/ 四件套 + ADR + DDD 模块
❌ 错误 2：正式产品跳过架构设计，直接在单个目录堆代码

✅ 正确：按规模分级执行——S 级精简流程、M 级标准流程、L 级完整架构；
        涉及支付/认证/敏感数据时无条件升级到 L 级门禁
```

### 反模式 6：重复造轮子

```
❌ 错误：每个业务模块各自写一套 axios 封装、错误处理、工具函数

✅ 正确：新增功能前按序检查 Core → 已有模块 → Plugins；
        网络请求必须走 core/http，认证走 core/auth，禁止业务层直连底层库
```

### 反模式 7：遇到异常只报错不恢复

```
❌ 错误：web_search 超时后输出"查询失败，无法继续"并停止
❌ 错误：依赖安装失败后反复盲目重试同一命令
❌ 错误：AI 会话中断后让用户从头开始选型

✅ 正确：① 回退到备选方案（内置基线/镜像源/进度文件）并继续流程；
        ② 用"⚠️问题→✅已处理→👉下一步"三段式提示用户；
        ③ 连续失败 3 次暂停并保留诊断输出请用户介入；
        ④ 进度已持久化到 .agent/selection-progress.md，断点可恢复
```

### 反模式 8：国内项目硬套国外部署 / 不提供国内回退方案（国内适配反模式）

```
❌ 错误 1：选型阶段四候选只列 AWS / Vercel / Heroku / Cloudflare，不提国内云厂商
❌ 错误 2：依赖安装失败时不主动建议国内镜像，反复跑官方源超时
❌ 错误 3：AI 模型 API 只推荐 OpenAI / Anthropic，不告知国产替代
❌ 错误 4：Git clone github.com 超时直接报错，不提示代理或镜像站
❌ 错误 5：国内部署却用未备案域名，导致访问不通或下架

✅ 正确：① 部署候选必须腾讯云 / 阿里云 / 华为云 与境外方案并列，由用户决定；
        ② 依赖安装默认询问是否配置国内镜像（详见"环境与工具适配"表）；
        ③ AI 模型 API 必须国产替代与境外并列（DeepSeek / 智谱 / 通义 / 文心 / Kimi），Core 抽象统一接口；
        ④ Git 克隆失败回退 ghproxy / gitclone 镜像；
        ⑤ 国内部署必须使用已 ICP 备案域名
```

### 反模式 9：规模升降级时不更新架构 / 静默演进（规模切换反模式）

```
❌ 错误 1：脚本演变成正式产品后，仍按 S 级门禁开发，不补 .agent/ 与 ADR
❌ 错误 2：L 级项目人员缩减后强制拆除已有架构，重写为单目录
❌ 错误 3：选型完成后引入 Redis、RabbitMQ 等未选型技术，不补选型流程
❌ 错误 4：规模发生变化时不告知用户当前级别与目标级别的差异

✅ 正确：① 升级时按目标级别补齐门禁产物，已生成代码不重写，仅补缺漏；
        ② 降级时不强制拆除，标记"维持现状 + 降级目标"，新功能按降级目标执行；
        ③ 引入未选型技术走"补选流程"：动态调研 + 候选 + 用户确认 + 更新 architecture.md；
        ④ 任何规模变化必须先告知用户当前级别与目标级别差异，再问是否继续
```

## 禁忌用法清单

以下行为在任何场景下都不允许：

1. **跳过需求分析直接给技术方案** — 即使需求看起来"显而易见"
2. **静默跳过选型层级** — 已选框架覆盖的层级也必须询问用户（内置 / 独立方案 / 无）
3. **自动填充或锁定任何选项** — 选择权永远属于用户
4. **复用旧搜索结果** — 每次确认后必须基于全部累计上下文重新 web_search
5. **把独立决策预绑定为单个候选** — 如 `Node.js + TypeScript`、`Vue + Pinia`
6. **随意修改 Core 层** — 必须说明原因、影响范围、兼容与迁移方案
7. **删除代码前不检查引用** — 先检查引用关系、历史兼容、API 影响
8. **未理解项目结构就写代码** — 必须先阅读 README / .agent / 目录结构 / 依赖配置
9. **无理由增加技术依赖** — 依赖必须由需求驱动，而非"为了先进"
10. **裁剪生命周期阶段但不说明原因** — 任何被裁剪的阶段都必须在总结中说明
11. **遇到异常只报错不恢复** — 必须给出回退方案和下一步动作，禁止让用户自行判断
12. **国内项目只列国外部署/国外镜像不提供国内回退** — 部署、依赖、Git、AI 模型 API 均须国内方案与境外并列
13. **规模升降级不更新架构或静默处理** — 升级补门禁、降级标记演进目标、变更必先告知差异
14. **选型完成后引入未选型技术不走补选流程** — 新依赖必须走动态调研 + 用户确认，禁止静默引入
15. **静默决策未列出的边界场景** — 未覆盖的新场景必须"先告知边界、再问用户决定"

## 红线自检清单（每次任务完成前）

- [ ] 是否先理解了项目上下文（README / .agent / 依赖配置）？
- [ ] 是否完成了规模分级与类型判定？
- [ ] 每个选型层级是否都让用户确认了？
- [ ] 是否实时查询了版本号而非沿用历史版本？
- [ ] 新增功能前是否检查了 Core → 已有模块 → Plugins？
- [ ] 是否有重要技术决策未记录 ADR？
- [ ] 新功能是否有单元测试 + 集成测试？
- [ ] 是否有硬编码的敏感信息？
- [ ] 遇到异常是否给出了回退方案和下一步，而非只报错？
- [ ] 国内项目的部署 / 依赖 / Git / AI 模型 API 是否都列了国内回退方案？
- [ ] 规模发生变化时是否先告知当前级别与目标级别差异？
- [ ] 选型完成后引入新技术是否走了补选流程（动态调研 + 用户确认 + 更新 architecture.md）？
- [ ] 边界场景（未在能力边界明细中明确列出）是否走了"先告知、再问用户决定"流程？
