# 开发生命周期与规范

> AI 开发生命周期、代码修改规则、测试、安全、文档的详细参考文档。
> 在编写代码、创建测试或建立开发标准时加载本文档。

---

## 1. AI 开发生命周期

任何任务必须经过全部 6 个阶段：

### Phase 1 理解

读取：
- 项目文档（README.md、.agent/context.md、.agent/architecture.md、.agent/coding-rule.md）
- 相关模块
- 已有代码

### Phase 2 分析

确认：
- 是否已有可用能力？
- 能否复用已有代码？
- 哪些模块受影响？
- 是否需要新增架构？

### Phase 3 设计

输出：
- 修改文件
- 新增文件
- 删除文件
- 影响范围
- 风险

### Phase 4 实现

要求：
- 小范围修改
- 保持项目风格
- 避免无关重构

### Phase 5 验证

执行：
- Lint（代码风格检查）
- Type Check（类型安全）
- Test（单元测试、集成测试、核心流程测试）
- Build（编译与打包）

### Phase 6 总结

输出：
- 修改内容
- 修改原因
- 影响范围
- 测试结果
- 后续建议

## 2. Git 工作流规范

### 分支策略

| 分支 | 用途 | 规则 |
|------|------|------|
| `main` / `master` | 生产就绪代码 | 只接受 PR/MR 合入，禁止直接推送 |
| `develop` | 集成分支（可选，小团队可省略） | 功能分支的汇合点 |
| `feature/<scope>-<desc>` | 新功能 | 从 main/develop 切出，完成后 PR 合回 |
| `fix/<issue>-<desc>` | 缺陷修复 | 同上 |
| `chore/<desc>` | 构建、依赖、杂务 | 同上 |

小团队 / 个人项目可直接用 `main + feature/*` 两级，不强制 `develop`。

### Commit 规范（Conventional Commits）

```
<type>(<scope>): <subject>

type: feat | fix | refactor | docs | test | chore | perf | style
示例: feat(order): 支持订单取消原因备注
```

规则：

- 一个 commit 只做一件事；AI Agent 完成一个 Phase 4 实现后应建议独立提交
- subject 用祈使句、≤ 72 字符
- 破坏性变更在 footer 标注 `BREAKING CHANGE:`

## 3. 代码修改规则

### 小范围修改原则

**禁止：** 一次修改大量无关代码。

### Core 修改规则

修改 Core 必须记录：

1. **修改原因** — 为什么需要修改
2. **影响范围** — 哪些模块受影响
3. **兼容方案** — 现有代码如何继续工作
4. **迁移方案** — 如何过渡到新版本

### 删除规则

删除代码前，检查：

- **引用关系** — 该代码是否被其他地方引用？
- **历史兼容** — 是否有外部依赖？
- **API 影响** — 是否影响公共 API？

## 4. 测试规范

### 必需的测试类型

新增功能必须包含：

| 测试类型 | 范围 |
|----------|------|
| 单元测试 | 单个函数、方法、类 |
| 集成测试 | 模块交互、API 端点 |
| 核心流程测试 | 端到端关键业务路径 |

### 覆盖要求

测试必须覆盖：

- **正常流程** — 预期用例
- **异常流程** — 错误处理、无效输入
- **边界情况** — 边缘条件、极限值

---

## 5. 安全规范

### 禁止

- 代码中硬编码密码
- 提交 API Key 到仓库
- 在源码中暴露数据库凭据
- 在日志中输出敏感信息

### 必须

- **环境变量** — 所有机密和配置使用环境变量
- **权限校验** — 所有敏感操作进行权限验证
- **输入验证** — 所有外部输入进行验证
- **日志脱敏** — 在日志中屏蔽敏感数据
- **安全审计** — 定期审查访问模式

## 6. README 规范

项目必须包含 README.md：

1. **项目介绍** — 项目是什么及做什么
2. **技术架构** — 技术栈和架构概览
3. **目录说明** — 关键目录解释
4. **开发环境** — 前置条件和设置
5. **启动方式** — 如何本地运行
6. **部署方式** — 如何部署到生产环境
7. **开发规范** — 编码约定和规则
8. **AI Agent 规则** — AI Agent 的工作指南

### 架构说明模板

```
本项目采用：Core + Business Module 架构

核心原则：
- 公共能力统一维护
- 业务模块独立开发
- 禁止重复建设

Core 目录职责：
- auth: 认证与授权
- http: 网络请求处理
- ui: 共享 UI 组件
- utils: 工具函数
- storage: 数据持久化
- error: 异常处理
- logger: 日志系统
- config: 配置管理

新功能开发流程：
1. 检查 Core 能力
2. 检查已有模块
3. 优先复用
4. 新增业务代码
5. 补充文档
```

## 7. AI Agent 行为协议

### 进入项目时

**必须：**

1. 阅读文档
2. 理解架构
3. 优先复用
4. 保持项目风格
5. 记录变化

**禁止：**

1. 创建重复结构
2. 重复造轮子
3. 破坏已有设计
4. 无理由升级依赖

## 8. 架构演进原则

### 长期架构层次

| 层次 | 特征 |
|------|------|
| 稳定核心层 | 极少变化、高复用、所有模块的基础 |
| 快速业务层 | 快速迭代、独立模块、DDD 结构 |
| 插件扩展层 | 可选能力、可插拔、隔离 |
| AI 自动化层 | 自动化测试、部署、代码质量检查 |

### 最终目标

构建 **AI Native Software System**，具备：

- **可维护** — 清晰的结构、文档化的决策
- **可扩展** — 模块化设计、插件架构
- **可复用** — Core 能力跨模块共享
- **可测试** — 各层全面的测试覆盖
- **可持续 AI 开发** — AI Agent 可持续贡献而不降低质量
