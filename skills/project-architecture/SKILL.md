# AI Native Project Architecture Skill V5.0

> 企业级 AI Coding Agent 项目初始化、架构设计、持续开发规范。
>
> 适用于：OpenAI Codex / Claude Code / CodeBuddy / Cursor Agent / OpenCode / Devin 类 AI 软件工程 Agent。

---

# 一、Skill 定位

指导 AI Agent 按资深技术架构师标准完成：项目初始化、技术选型、架构设计、模块规划、代码开发、项目维护、架构演进。

核心目标：技术选型合理、业务与技术解耦、公共能力复用、降低系统复杂度、提升 AI 持续开发能力、保证长期可维护性。

核心原则：

- 先理解，再设计
- 先架构，再编码
- 先抽象，再实现
- 先复用，再扩展
- 先验证，再提交

# 二、三档用户模式（开场必做）

AI Agent 首次接触用户时，必须先用一句话确认用户类型，并切换到对应交互模式：

| 模式 | 用户画像 | 交互方式 |
|------|----------|----------|
| 🌱 引导模式 | 技术小白 / 非技术人员 | 全程大白话，每层给出"推荐项 + 一句人话解释"，用户只需回答"用推荐"即可完成全部选型；不解释术语除非用户问 |
| 📋 产品模式 | 产品经理 / 业务方 | 聚焦业务需求梳理（用户、流程、数据、边界），输出领域模型草图；技术选型只给结论清单和理由摘要，不逐层打断 |
| ⚡ 专家模式 | 开发者 / 技术负责人 | 直接逐层确认关键分歧点，默认项自动填充，快速输出完整技术栈清单 |

模式判定信号：

- 用户说"我想做个 XX，但我不懂技术" → 引导模式
- 用户给的是 PRD / 业务描述 / 原型图 → 产品模式
- 用户直接说技术名词（"用 Vue 还是 React"）→ 专家模式
- 无法判断时直接问："为了给你最合适的方式，你更偏向：A. 我不懂技术，你帮我定 B. 我懂业务，技术你推荐 C. 我是开发者，咱们快速过"

# 三、规模分级（反过度工程）

**不是所有项目都需要完整架构。** 开工前必须先判定项目规模，禁止给小项目套大架构：

| 级别 | 判定信号 | 架构策略 |
|------|----------|----------|
| S 级：脚本 / 原型 / 一次性工具 | 单文件可完成、无部署需求、用完即弃 | 直接写，不建 Core/模块/ADR，只写最小 README |
| M 级：小型应用 / 个人项目 | 1-3 个功能模块、单人开发、生命周期 < 6 个月 | 简化结构：`src/` + `README.md`，可选 `.agent/context.md`，不写 ADR |
| L 级：正式产品 / 团队协作 | 多模块、多人协作、长期维护、有部署运维 | 完整架构：Core + DDD 模块 + ADR + 6 阶段生命周期 |

**默认假设为 M 级**，仅在信号明确时升级到 L 级（用户提到团队协作、长期维护、企业级、多人开发等）。禁止默认上完整架构。

# 四、AI Agent 最高执行原则

任何 AI Agent 进入项目，必须按以下流程执行：

1. 阅读项目文档 → 2. 分析项目结构 → 3. 理解已有架构 → 4. 检查已有能力 → 5. 设计修改方案 → 6. 执行开发 → 7. 验证结果 → 8. 输出总结

禁止：

- 未理解项目直接写代码
- 根据一句需求直接生成完整功能
- 重复创建已有能力
- 随意修改核心架构
- 无理由增加技术依赖
- 大范围无目的重构

# 五、项目上下文管理

AI Agent 必须优先读取以建立项目认知：

```
.agent/
├── context.md          # 项目定位与业务背景
├── architecture.md     # 架构决策与结构说明
├── coding-rule.md      # 编码规范
├── workflow.md         # 开发工作流
└── docs/adr/           # 架构决策记录
```

以及：`README.md`、项目目录结构、依赖配置文件（`package.json` / `pom.xml` / `go.mod` / `requirements.txt`）。

AI 必须明确：项目定位、业务目标、技术架构、核心模块、公共能力、技术约束、部署方式、潜在风险。

**新项目初始化时**：用 `templates/` 目录下的模板生成 `.agent/` 四件套和 README，不允许凭空编写。

# 六、需求分析规范

任何需求必须拆分为：

```
业务需求层 → 领域模型层 → 应用服务层 → 技术实现层 → 基础设施层
```

禁止：业务描述直接映射技术方案。

错误示范：

```
用户："我要开发商城系统"
AI："使用 Vue + SpringBoot + MySQL"   ← 错误，跳过了业务分析
```

正确流程：先分析业务（用户、商品、订单、支付、库存、营销），再设计技术（前端框架、后端框架、数据库、缓存、消息、权限、部署）。

产品模式下，此阶段输出物为**领域模型草图 + 用户核心流程**，需用户确认后才进入技术选型。

# 七、技术选型总览

技术选型采用**逐层交互式勾选 + 能力感知 + 联动推荐**模式：使用 `ask_followup_question` 工具让用户通过勾选完成选型，而非纯文字推荐；选型过程中感知已选框架的能力覆盖范围，在后续层级标注"已覆盖"提示；联动推荐兼容的配套框架和插件。

## 7.1 最高原则：选择权永远属于用户（强制）

**AI Agent 是智能大脑，只给出推荐，不代替用户选择。** 除非用户明确要求"你帮我自动选择"，否则每一层都必须让用户自行勾选确认。

**禁止行为：**
- 自动填充任何层级的选择（即使看起来是"显而易见"的选择）
- 自动锁定任何层级（即使框架生态只有一个主流方案）
- 跳过任何层级不询问用户（即使已选框架已覆盖该能力）
- 预选/默认勾选任何选项（推荐项仅通过标注"推荐"提示，不代替用户勾选）

**正确行为：**
- 每一层都通过 `ask_followup_question` 让用户选择
- 推荐项标注"推荐"标签和一句话理由，但选择权归用户
- 已选框架覆盖的层级，仍需询问用户是否使用内置能力还是选择独立方案
- 用户可随时说"剩下的你帮我自动选择"来授权 AI 批量选择

## 7.2 交互式选型流程（强制）

**AI Agent 必须使用 `ask_followup_question` 工具进行技术选型**，禁止仅用文字表格让用户口头确认。

### 问题前缀强制规则（强制）

**所有选型问题的 `header`（标题）必须以"前端-"或"后端-"前缀开头**，禁止使用无前缀的标题（如"状态管理"、"缓存方案"），避免用户混淆前后端层级。

正确示例：`"前端-状态管理"`、`"后端-缓存方案"`、`"前端-UI 组件库"`、`"后端-ORM/数据访问"`
错误示例：`"状态管理"`、`"缓存方案"`、`"UI 组件库"`、`"ORM/数据访问"`

### 前后端分离选型规则（强制）

**前端和后端的逐层选型必须分阶段进行，禁止在同一批问题中混合前端和后端层级。**

- 必须先完整选完前端所有层级，再开始后端选型
- 每批问题只能属于同一端（全前端或全后端），禁止混批
- 前端选型完成后，明确告知用户"前端技术栈已确认完毕，接下来进入后端技术选型"，再开始后端选型

### 选型分三阶段

### 阶段一：技术栈核心选择（跨端批量勾选）

一次性向用户展示前端主框架、后端主语言、数据库、部署方案等核心选型，用户通过勾选完成。此阶段允许跨端混合，因为这些是全局决策：

```
ask_followup_question({
  questions: [
    { question: "前端主框架？", header: "前端-主框架", options: ["Vue", "React", "Svelte"], multiSelect: false },
    { question: "后端主语言？", header: "后端-主语言", options: ["Node.js (TypeScript)", "Java", "Go", "Python"], multiSelect: false },
    { question: "数据库？", header: "数据库", options: ["MySQL", "PostgreSQL", "MongoDB"], multiSelect: false },
    { question: "部署方案？", header: "部署方案", options: ["Docker Compose", "Docker", "云平台托管"], multiSelect: false },
    ...
  ]
})
```

### 阶段二：前端逐层拓展选择（仅前端，联动勾选）

根据阶段一的前端主框架选择结果，**逐层**展示前端兼容的候选方案，每层都让用户选择。**此阶段所有问题只包含前端层级，禁止混入后端层级。**

```
ask_followup_question({
  questions: [
    { question: "前端开发语言？", header: "前端-开发语言", options: [
      "TypeScript（推荐：类型安全、IDE 智能提示）",
      "JavaScript（无编译开销、学习门槛低）"
    ], multiSelect: false },
    { question: "前端构建工具？", header: "前端-构建工具", options: [
      "Vite（推荐：极速 HMR、Vue 官方推荐）",
      "Webpack（生态成熟、遗留项目）"
    ], multiSelect: false },
    { question: "前端 UI 组件库？", header: "前端-UI 组件库", options: [
      "Element Plus（推荐：Vue 3 生态成熟、中文社区大）",
      "Naive UI",
      "Ant Design Vue"
    ], multiSelect: false },
    ...
  ]
})
```

前端所有层级选完后，明确告知用户：

> 前端技术栈已确认完毕。接下来进入后端技术选型。

### 阶段三：后端逐层拓展选择（仅后端，联动勾选）

根据阶段一的后端主语言选择结果，**逐层**展示后端兼容的候选方案，每层都让用户选择。**此阶段所有问题只包含后端层级，禁止混入前端层级。**

```
ask_followup_question({
  questions: [
    { question: "后端框架？", header: "后端-框架", options: [
      "NestJS（推荐：模块化、TS 原生、IoC 容器）",
      "Express（最轻量、生态最大）",
      "Fastify（性能优先、Schema 验证）"
    ], multiSelect: false },
    { question: "后端 API 规范？", header: "后端-API 规范", options: [
      "RESTful（推荐：通用标准、前端友好）",
      "GraphQL（灵活查询、按需获取）",
      "gRPC（高性能、强类型）"
    ], multiSelect: false },
    { question: "后端 ORM/数据访问？", header: "后端-ORM/数据访问", options: [
      "Prisma（推荐：类型安全、Schema 优先）",
      "TypeORM（装饰器风格）",
      "Drizzle ORM（轻量、SQL 风格）"
    ], multiSelect: false },
    ...
  ]
})
```

**关键规则：**
- 每批 3-4 个勾选问题，避免一次展示过多
- 每个选项标注"推荐"标签和一句话理由
- **所有问题 header 必须带"前端-"或"后端-"前缀**（阶段一的全局决策除外）
- **同一批问题禁止混合前端和后端层级**（阶段一的全局决策除外）
- 已选框架覆盖的层级，将"使用内置"作为推荐项展示，但仍需用户确认
- 配套插件以多选勾选形式展示，用户按需勾选

## 7.3 能力感知与冗余提示（强制）

**AI Agent 必须感知已选框架自带的能力，在后续层级标注"已覆盖"提示。**

核心规则：

1. **能力覆盖检测** — 用户选择某框架后，AI Agent 检查该框架是否已覆盖后续某层的能力
2. **覆盖提示** — 若已覆盖，该层仍需询问用户，但将"使用内置"作为推荐项标注"已覆盖"
3. **升级提示** — 若用户需求超出内置能力，推荐独立方案并说明"内置能力不足时选择"
4. **多选插件** — 配套插件以多选勾选形式展示，用户按需勾选

常见能力覆盖关系（完整矩阵见 `references/tech-stack-guide.md` 第 2.3 节）：

| 已选框架 | 覆盖的层级 | 推荐策略 |
|----------|-----------|----------|
| Element Plus (Vue) | L9 表单验证 | 推荐"使用内置验证"，但仍需用户确认 |
| Ant Design (React) | L9 表单验证 | 推荐"使用内置验证"，但仍需用户确认 |
| NestJS | L8 认证 | 推荐 `@nestjs/passport`，但仍需用户确认 |
| Vue Router | L8 路由 | 推荐 Vue Router，但仍需用户确认 |
| SvelteKit | L8 路由 + L3 构建 | 推荐 SvelteKit 内置，但仍需用户确认 |
| Next.js | L3 构建 + L8 路由 | 推荐 Next.js 内置，但仍需用户确认 |

## 7.4 分层联动规则

**前序选择影响后序可选项和推荐，但不代替用户选择。**

- 选 Vue → L4 展示 Vue 生态组件库候选，L7 推荐 Pinia，L8 推荐 Vue Router — 均需用户确认
- 选 React → L4 展示 React 生态组件库候选，L7 推荐 Zustand/Redux Toolkit，L8 推荐 React Router — 均需用户确认
- 选 Svelte → L4 展示 Svelte 生态组件库候选，L7 推荐 Svelte Stores，L8 推荐 SvelteKit 路由 — 均需用户确认
- 选 Node.js → L4 展示 Node 生态 ORM 候选，L9 推荐 Pino — 均需用户确认
- 选 Java → L4 展示 Java 生态 ORM 候选，L9 推荐 Logback — 均需用户确认
- 选 Go → L4 展示 Go 生态 ORM 候选，L9 推荐 Zap — 均需用户确认

**关键：** "推荐"不等于"自动选择"。每一层都必须让用户勾选确认。

## 7.5 选型层级与顺序（强制）

**选型顺序强制规则：阶段一（核心选择）→ 阶段二（前端全部层级）→ 阶段三（后端全部层级）→ 跨端关注点。禁止打乱顺序。**

### 阶段一：核心选择（跨端，可混合）

全局决策项，允许在同一批中混合：
- 前端主框架、后端主语言、数据库、部署方案

### 阶段二：前端全部层级（按顺序，禁止混入后端）

**前端-主框架** → **前端-开发语言** → **前端-构建工具** → **前端-UI 组件库** → **前端-CSS 方案** → **前端-网络请求库** → **前端-状态管理** → **前端-路由** → **前端-表单验证**（可能被 UI 库覆盖，但仍需确认）→ **前端-测试框架** → **前端-代码质量工具** → **前端-国际化**（按需）

### 阶段三：后端全部层级（按顺序，禁止混入前端）

**后端-主语言**（阶段一已选）→ **后端-框架** → **后端-API 规范** → **后端-ORM/数据访问** → **后端-数据库**（阶段一已选）→ **后端-缓存** → **后端-消息队列** → **后端-认证** → **后端-日志** → **后端-测试框架** → **后端-文件存储**（按需）→ **后端-定时任务**（按需）

### 阶段四：跨端关注点

**前后端选型全部完成后**，引导选择 CI/CD 方案和错误监控/APM 方案。

## 7.6 交互规则按模式调整

- **引导模式**：每批 3-4 个勾选问题，每项标注"推荐"和一句人话解释，用户勾选确认
- **产品模式**：分批展示推荐清单，每项标注"推荐"，用户逐批确认或微调
- **专家模式**：分批勾选，每批展示更多候选（Top 3-5），推荐项标注"推荐"，用户逐层选择
- **任何模式**：动态版本解析（`npm view <pkg> version` / Maven Central / Go Module Proxy / PyPI），禁止沿用历史版本号
- **任何模式**：禁止自动填充、自动锁定、跳过层级。所有层级必须由用户确认
- **任何模式**：所有问题 header 必须带"前端-"或"后端-"前缀（阶段一全局决策除外）
- **任何模式**：同一批问题禁止混合前端和后端层级（阶段一全局决策除外），前端全部选完后再选后端

详细候选方案、能力覆盖矩阵、兼容性矩阵、联动规则、子插件推荐见 `references/tech-stack-guide.md`。

# 八、项目整体架构

L 级项目统一采用：**Core + Business Module + Plugin + Infrastructure + Documentation + Test**

```
project
├── core              # 核心基础能力（前后端结构不同，见 references）
├── modules           # 业务模块（DDD）
├── plugins           # 插件扩展
├── infrastructure    # 基础设施层
├── config            # 全局配置
├── docs              # 文档（含 ADR）
├── tests             # 测试
└── README.md
```

关键规范（详细见 `references/architecture-design.md`）：

- **Core**：稳定、通用、低变化、高复用；禁止包含业务代码；前端 Core 与后端 Core 结构不同
- **业务模块**：DDD 四层 `domain / application / infrastructure / interfaces`
- **复用规则**：新增功能前按序检查 Core → 已有模块 → Plugins，禁止重复造轮子
- **ADR**：所有重要技术决策记录到 `docs/adr/`，格式见 `references/architecture-design.md` 第 5 节

# 九、AI 开发生命周期

任何任务必须经过 6 个阶段（详细见 `references/dev-lifecycle.md`）：

1. **理解** — 读文档、相关模块、已有代码
2. **分析** — 是否已有能力、可否复用、影响范围、是否需新增架构
3. **设计** — 输出修改/新增/删除文件清单、影响范围、风险
4. **实现** — 小范围修改、保持项目风格、避免无关重构
5. **验证** — Lint → Type Check → Test → Build
6. **总结** — 修改内容、原因、影响范围、测试结果、后续建议

Git 工作流（分支策略、Commit 规范）见 `references/dev-lifecycle.md` 第 2 节。

# 十、关键红线（各模式通用）

- **测试**：新功能必须有单元测试 + 集成测试，覆盖正常/异常/边界
- **安全**：禁止硬编码密码、提交 API Key、暴露数据库账号、输出敏感日志；必须环境变量管理、权限控制、输入验证、日志脱敏
- **Core 修改**：必须说明修改原因、影响范围、兼容方案、迁移方案
- **删除代码**：先检查引用关系、历史兼容、API 影响
- **README**：项目必须包含 README.md（8 要素见 `references/dev-lifecycle.md` 第 6 节）
