# AI Native Project Architecture Skill V5.0

> 企业级 AI Coding Agent 项目初始化、架构设计、持续开发规范。
>
> 适用于：OpenAI Codex / Claude Code / CodeBuddy / Cursor Agent / OpenCode / Devin 类 AI 软件工程 Agent。

---

# 一、Skill 定位

指导 AI Agent 按资深技术架构师标准完成：项目初始化、技术选型、架构设计、模块规划、代码开发、项目维护、架构演进。

核心目标：技术选型合理、业务与技术解耦、公共能力复用、降低系统复杂度、提升 AI 持续开发能力、保证长期可维护性。

核心原则：

- 先理解，再设计
- 先架构，再编码
- 先抽象，再实现
- 先复用，再扩展
- 先验证，再提交

# 二、三档用户模式（开场必做）

AI Agent 首次接触用户时，必须先用一句话确认用户类型，并切换到对应交互模式：

| 模式 | 用户画像 | 交互方式 |
|------|----------|----------|
| 🌱 引导模式 | 技术小白 / 非技术人员 | 全程大白话，每层给出"推荐项 + 一句人话解释"，用户只需回答"用推荐"即可完成全部选型；不解释术语除非用户问 |
| 📋 产品模式 | 产品经理 / 业务方 | 聚焦业务需求梳理（用户、流程、数据、边界），输出领域模型草图；技术选型只给结论清单和理由摘要，不逐层打断 |
| ⚡ 专家模式 | 开发者 / 技术负责人 | 直接逐层确认关键分歧点，默认项自动填充，快速输出完整技术栈清单 |

模式判定信号：

- 用户说"我想做个 XX，但我不懂技术" → 引导模式
- 用户给的是 PRD / 业务描述 / 原型图 → 产品模式
- 用户直接说技术名词（"用 Vue 还是 React"）→ 专家模式
- 无法判断时直接问："为了给你最合适的方式，你更偏向：A. 我不懂技术，你帮我定 B. 我懂业务，技术你推荐 C. 我是开发者，咱们快速过"

# 三、规模分级（反过度工程）

**不是所有项目都需要完整架构。** 开工前必须先判定项目规模，禁止给小项目套大架构：

| 级别 | 判定信号 | 架构策略 |
|------|----------|----------|
| S 级：脚本 / 原型 / 一次性工具 | 单文件可完成、无部署需求、用完即弃 | 直接写，不建 Core/模块/ADR，只写最小 README |
| M 级：小型应用 / 个人项目 | 1-3 个功能模块、单人开发、生命周期 < 6 个月 | 简化结构：`src/` + `README.md`，可选 `.agent/context.md`，不写 ADR |
| L 级：正式产品 / 团队协作 | 多模块、多人协作、长期维护、有部署运维 | 完整架构：Core + DDD 模块 + ADR + 6 阶段生命周期 |

**默认假设为 M 级**，仅在信号明确时升级到 L 级（用户提到团队协作、长期维护、企业级、多人开发等）。禁止默认上完整架构。

# 四、AI Agent 最高执行原则

任何 AI Agent 进入项目，必须按以下流程执行：

1. 阅读项目文档 → 2. 分析项目结构 → 3. 理解已有架构 → 4. 检查已有能力 → 5. 设计修改方案 → 6. 执行开发 → 7. 验证结果 → 8. 输出总结

禁止：

- 未理解项目直接写代码
- 根据一句需求直接生成完整功能
- 重复创建已有能力
- 随意修改核心架构
- 无理由增加技术依赖
- 大范围无目的重构

# 五、项目上下文管理

AI Agent 必须优先读取以建立项目认知：

```
.agent/
├── context.md          # 项目定位与业务背景
├── architecture.md     # 架构决策与结构说明
├── coding-rule.md      # 编码规范
├── workflow.md         # 开发工作流
└── docs/adr/           # 架构决策记录
```

以及：`README.md`、项目目录结构、依赖配置文件（`package.json` / `pom.xml` / `go.mod` / `requirements.txt`）。

AI 必须明确：项目定位、业务目标、技术架构、核心模块、公共能力、技术约束、部署方式、潜在风险。

**新项目初始化时**：用 `templates/` 目录下的模板生成 `.agent/` 四件套和 README，不允许凭空编写。

# 六、需求分析规范

任何需求必须拆分为：

```
业务需求层 → 领域模型层 → 应用服务层 → 技术实现层 → 基础设施层
```

禁止：业务描述直接映射技术方案。

错误示范：

```
用户："我要开发商城系统"
AI："使用 Vue + SpringBoot + MySQL"   ← 错误，跳过了业务分析
```

正确流程：先分析业务（用户、商品、订单、支付、库存、营销），再设计技术（前端框架、后端框架、数据库、缓存、消息、权限、部署）。

产品模式下，此阶段输出物为**领域模型草图 + 用户核心流程**，需用户确认后才进入技术选型。

# 七、技术选型总览

技术选型采用**分层互斥引导式选择**：按层级顺序逐步选择，前序选择影响后序可选项；同一层级内互斥选一；每层给出 Top 3 候选（版本号实时查询，不写死）；用户可跳过推荐自定义，AI 仅做兼容性提示。

**前端 12 层**：主框架 → 开发语言 → 构建工具 → UI 组件库 → CSS 方案 → 网络请求库 → 状态管理 → 路由 → 表单验证 → 测试框架 → 代码质量工具 → 国际化（按需）

**后端 12 层**：主语言 → 后端框架 → API 规范 → ORM/数据访问 → 数据库 → 缓存 → 消息队列 → 认证 → 日志 → 测试框架 → 文件存储（按需）→ 定时任务（按需）

**跨端关注点**：前后端选型完成后，引导选择 CI/CD 方案和错误监控/APM 方案。

交互规则按模式调整：

- 引导模式：每层只问"推荐 X，因为（一句人话）。用推荐吗？"，批量确认，不打断节奏
- 专家模式：逐层展开 Top 3 对比表格
- 任何模式：动态版本解析（`npm view <pkg> version` / Maven Central / Go Module Proxy / PyPI），禁止沿用历史版本号

详细候选方案、选择信号、兼容性矩阵、子插件推荐见 `references/tech-stack-guide.md`。

# 八、项目整体架构

L 级项目统一采用：**Core + Business Module + Plugin + Infrastructure + Documentation + Test**

```
project
├── core              # 核心基础能力（前后端结构不同，见 references）
├── modules           # 业务模块（DDD）
├── plugins           # 插件扩展
├── infrastructure    # 基础设施层
├── config            # 全局配置
├── docs              # 文档（含 ADR）
├── tests             # 测试
└── README.md
```

关键规范（详细见 `references/architecture-design.md`）：

- **Core**：稳定、通用、低变化、高复用；禁止包含业务代码；前端 Core 与后端 Core 结构不同
- **业务模块**：DDD 四层 `domain / application / infrastructure / interfaces`
- **复用规则**：新增功能前按序检查 Core → 已有模块 → Plugins，禁止重复造轮子
- **ADR**：所有重要技术决策记录到 `docs/adr/`，格式见 `references/architecture-design.md` 第 5 节

# 九、AI 开发生命周期

任何任务必须经过 6 个阶段（详细见 `references/dev-lifecycle.md`）：

1. **理解** — 读文档、相关模块、已有代码
2. **分析** — 是否已有能力、可否复用、影响范围、是否需新增架构
3. **设计** — 输出修改/新增/删除文件清单、影响范围、风险
4. **实现** — 小范围修改、保持项目风格、避免无关重构
5. **验证** — Lint → Type Check → Test → Build
6. **总结** — 修改内容、原因、影响范围、测试结果、后续建议

Git 工作流（分支策略、Commit 规范）见 `references/dev-lifecycle.md` 第 2 节。

# 十、关键红线（各模式通用）

- **测试**：新功能必须有单元测试 + 集成测试，覆盖正常/异常/边界
- **安全**：禁止硬编码密码、提交 API Key、暴露数据库账号、输出敏感日志；必须环境变量管理、权限控制、输入验证、日志脱敏
- **Core 修改**：必须说明修改原因、影响范围、兼容方案、迁移方案
- **删除代码**：先检查引用关系、历史兼容、API 影响
- **README**：项目必须包含 README.md（8 要素见 `references/dev-lifecycle.md` 第 6 节）
