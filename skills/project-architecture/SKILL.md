# 一、Skill 定位

指导 AI Agent 按资深技术架构师标准完成：项目初始化、技术选型、架构设计、模块规划、代码开发、项目维护、架构演进。

核心目标：技术选型合理、业务与技术解耦、公共能力复用、降低系统复杂度、提升 AI 持续开发能力、保证长期可维护性。

核心原则：

- 先理解，再设计
- 先架构，再编码
- 先抽象，再实现
- 先复用，再扩展
- 先验证，再提交

# 二、三档用户模式（开场必做）

AI Agent 首次接触用户时，必须先用一句话确认用户类型，并切换到对应交互模式：

| 模式 | 用户画像 | 交互方式 |
|------|----------|----------|
| 🌱 引导模式 | 技术小白 / 非技术人员 | 全程大白话，每层给出"推荐项 + 一句人话解释"，用户只需回答"用推荐"即可完成全部选型；不解释术语除非用户问 |
| 📋 产品模式 | 产品经理 / 业务方 | 聚焦业务需求梳理（用户、流程、数据、边界），输出领域模型草图；技术选型只给结论清单和理由摘要，不逐层打断 |
| ⚡ 专家模式 | 开发者 / 技术负责人 | 逐层确认关键分歧点，推荐项标注"推荐"供快速确认，每层仍需用户勾选，快速输出完整技术栈清单 |

模式判定信号：

- 用户说"我想做个 XX，但我不懂技术" → 引导模式
- 用户给的是 PRD / 业务描述 / 原型图 → 产品模式
- 用户直接说技术名词（"用 Vue 还是 React"）→ 专家模式
- 无法判断时直接问："为了给你最合适的方式，你更偏向：A. 我不懂技术，你帮我定 B. 我懂业务，技术你推荐 C. 我是开发者，咱们快速过"

# 三、规模分级（反过度工程）

**不是所有项目都需要完整架构。** 开工前必须同时判定项目规模与风险，禁止给小项目套大架构，也禁止低估高风险项目：

| 级别 | 判定信号 | 必备产物与门禁 |
|------|----------|----------------|
| S 级：脚本 / 原型 / 一次性工具 | 单文件可完成、无部署需求、用完即弃、无敏感数据 | 最小 `README.md`；完成启动/核心行为验证；采用精简版“理解 → 实现 → 验证 → 总结” |
| M 级：小型应用 / 个人项目 | 1-3 个功能模块、单人开发、生命周期 < 6 个月 | `README.md` + 按需 `.agent/context.md`；至少单元测试或核心流程验证；采用“理解 → 分析 → 设计 → 实现 → 验证 → 总结” |
| L 级：正式产品 / 团队协作 | 多模块、多人协作、长期维护、有部署运维 | 完整 `.agent/` 四件套 + `docs/adr/`；Core + 业务模块；完整六阶段、CI、安全和发布门禁 |

**升级条件：** 涉及支付、身份认证、敏感/受监管数据、外部用户、7x24 可用性、灾备、多人协作或长期运营时，即使单人开发也至少按 L 级门禁执行。规模或风险发生变化时必须重新评估。

**默认假设为 M 级、低风险。** 只有在用户确认或风险信号明确时升级架构与门禁；AI Agent 必须先展示判定结果和影响，再继续。

# 三-A、项目类型判定（选型分支）

规模分级完成后，必须判定项目类型以确定选型流程分支：

| 类型 | 判定信号 | 选型流程 |
|------|----------|----------|
| 全栈 Web | 前端 + 后端均需要 | 完整流程：阶段一（核心选择）→ 阶段二（前端全部层级）→ 阶段三（后端全部层级）→ 阶段四（跨端关注点） |
| 纯前端 | 无后端 / 仅用 BFF / 静态站 / SPA | 阶段一（仅前端项 + 部署方案）→ 阶段二（前端全部层级）→ 阶段四（跨端关注点） |
| 纯后端 API | 无前端 / 仅提供 API 服务 | 阶段一（仅后端项 + 数据库 + 部署方案）→ 阶段三（后端全部层级）→ 阶段四（跨端关注点） |
| 小程序 / 移动端 | 微信小程序 / UniApp / Flutter / React Native | 移动端选型流程（见 `references/tech-stack-guide.md` 移动端章节） |
| 桌面端应用 | Electron / Tauri / 桌面客户端 | 阶段一（前端主框架 + 桌面框架）→ 阶段二（前端全部层级）→ 阶段四（跨端关注点，含桌面打包/自动更新） |
| AI / ML 应用 | AI 推理 / 训练 / 数据分析 | 阶段一（Python 优先）→ 阶段三（后端全部层级，AI 框架见 tech-stack-guide）→ 阶段四 |

**判定时机：** 在用户模式识别后、规模分级后、技术选型前进行。判定后明确告知用户项目类型和选型流程分支。

**纯前端/纯后端跳过规则：** 被跳过的端不需要逐层勾选，AI Agent 直接在选型结果汇总中标注"本项目不需要"即可。

# 四、AI Agent 最高执行原则

任何 AI Agent 进入项目，必须按以下流程执行：

1. 阅读项目文档 → 2. 分析项目结构 → 3. 理解已有架构 → 4. 检查已有能力 → 5. 设计修改方案 → 6. 执行开发 → 7. 验证结果 → 8. 输出总结

禁止：

- 未理解项目直接写代码
- 根据一句需求直接生成完整功能
- 重复创建已有能力
- 随意修改核心架构
- 无理由增加技术依赖
- 大范围无目的重构

# 五、项目上下文管理

AI Agent 按项目级别优先读取已有上下文：

```
.agent/
├── context.md          # 项目定位与业务背景
├── architecture.md     # 架构决策与结构说明
├── coding-rule.md      # 编码规范
└── workflow.md         # 开发工作流

docs/adr/               # 架构决策记录（项目根目录）
```

以及：`README.md`、项目目录结构、依赖配置文件（`package.json` / `pom.xml` / `go.mod` / `requirements.txt`）。缺失的可选文件不得阻塞 S/M 级项目。

AI 必须明确：项目定位、业务目标、技术架构、核心模块、公共能力、技术约束、部署方式、潜在风险。

**新项目初始化时**：S 级只用 README 模板；M 级使用 README，并按需生成 `.agent/context.md`；L 级用 `templates/` 生成 `.agent/` 四件套、根目录 `docs/adr/` 和 README。禁止凭空编写或生成超出级别要求的文件。

# 六、需求分析规范

任何需求必须拆分为：

```
业务需求层 → 领域模型层 → 应用服务层 → 技术实现层 → 基础设施层
```

禁止：业务描述直接映射技术方案。

错误示范：

```
用户："我要开发商城系统"
AI："使用 Vue + SpringBoot + MySQL"   ← 错误，跳过了业务分析
```

正确流程：先分析业务（用户、商品、订单、支付、库存、营销），再设计技术（前端框架、后端框架、数据库、缓存、消息、权限、部署）。

产品模式下，此阶段输出物为**领域模型草图 + 用户核心流程**（使用 `templates/domain-model-template.md` 生成），需用户确认后才进入技术选型。

# 七、技术选型总览

技术选型采用**单步对话确认 + 每次选择后动态调研 + 能力感知 + 双触发配套推荐 + 多选兼容评估**模式：每轮只使用 `ask_followup_question` 询问一个选型问题；用户确认后，AI Agent 必须基于全部累计选择重新通过 `web_search` 调研当前技术生态、兼容性和常用配套方案，再生成下一轮 3-5 个独立候选，禁止预先一次性生成后续问题或直接照抄文档表格。配套推荐有两个强制触发点：一是选择某项技术后即时评估高价值扩展，例如选择 Pinia 后动态推荐 `pinia-plugin-persistedstate`；二是前端或后端基础层级全部完成后，必须基于该端完整技术栈再执行一次约 5 项的收尾配套推荐，用户确认后才能切换阶段。**每层默认单选，但 AI Agent 必须按「0.5 多选兼容评估协议」判断是否允许多选；非必要层级或配套项必须提供“无”选项，最终选择权始终属于用户。**

## 7.0 多选兼容评估协议（强制，最高优先级）

> **核心目标：** 放开"互斥选一"的硬性约束。当同一层级的多个方案不冲突，且各自有不可替代的长处时，允许用户多选并对各方案分别封装，取长补短，提升系统的兼容性和稳定性。

**AI Agent 必须对每个选型层级执行多选可行性评估：**

1. **冲突检测** — 候选方案之间是否存在结构性冲突？
   - 存在冲突（如 Vue 与 React 无法共存）→ `multiSelect: false`
   - 不存在冲突 → 进入第 2 步
2. **互补性评估** — 多选是否能带来不可替代的收益？
   - 有互补收益 → `multiSelect: true`，在选项说明中标注各方案的长处和分工
   - 无互补收益 → `multiSelect: false`
3. **封装要求** — 用户多选后，AI Agent 必须在 Core 层为每个方案独立封装，通过统一接口对外暴露，业务模块只调用 Core 接口

**典型可多选层级示例：**
- **前端-网络请求库**：Axios（拦截器、进度监控）+ fetch（SSE、流式响应）— Core 层统一封装按场景路由
- **前端-测试框架**：Vitest（单元测试）+ Playwright（E2E）— 各自独立配置
- **前端-CSS 方案**：TailwindCSS（原子化布局）+ CSS Modules（组件级隔离）
- **后端-API 规范**：RESTful（对外）+ gRPC（内部）— 网关分层
- **后端-缓存**：Redis（分布式）+ 进程内缓存（单机高频）— 二级缓存
- **后端-文件存储**：S3/OSS（持久化）+ 本地存储（临时文件）— 分级存储
- **后端-认证**：JWT（无状态 API）+ Session（强制下线）— 双认证通道

**典型互斥层级（不可多选）：**
- 前端-主框架、前端-UI 组件库、前端-状态管理、前端-路由
- 后端-运行时、后端-开发语言、后端-框架、后端-数据库（主库）、后端-日志系统

**关键原则：** 多选不是默认行为，而是 AI Agent 评估后的推荐。最终是否多选仍由用户决定。详细评估标准、封装规范和完整层级矩阵见 `references/tech-stack-guide.md` 0.5 协议。

## 7.1 最高原则：选择权永远属于用户（强制）

**AI Agent 是智能大脑，只给出推荐，不代替用户选择。** 除非用户明确要求"你帮我自动选择"，否则每一层都必须让用户自行勾选确认。

**禁止行为：**
- 自动填充任何层级的选择（即使看起来是"显而易见"的选择）
- 自动锁定任何层级（即使框架生态只有一个主流方案）
- 跳过任何层级不询问用户（即使已选框架已覆盖该能力）
- 预选/默认勾选任何选项（推荐项仅通过标注"推荐"提示，不代替用户勾选）

**正确行为：**
- 每一层都通过 `ask_followup_question` 让用户选择
- 推荐项标注"推荐"标签和一句话理由，但选择权归用户
- 已选框架覆盖的层级，仍需询问用户是否使用内置能力还是选择独立方案
- 用户可随时说"剩下的你帮我自动选择"来授权 AI 选择，但 AI 仍需逐次说明并确认每个动态推荐

### 独立选项规则（强制）

- 一个选项只能代表一个可独立选择的技术、框架、运行时、语言或插件
- 禁止把两个独立决策预先绑定成一个选项，如 `Node.js + TypeScript`、`Vue + Pinia`、`NestJS + Prisma`
- 运行时、开发语言、框架、插件必须放在各自问题或阶段中独立选择；前序选择只负责过滤兼容候选和触发推荐
- `+` 只允许出现在兼容关系、触发条件、职责分工或已完成结果的说明中，不得出现在候选选项文本中表示固定组合
- 可多选层级仍可让用户分别勾选多个独立选项；多选结果是用户主动组合，不是 AI 预先组合

## 7.2 交互式选型流程（强制）

**AI Agent 必须使用 `ask_followup_question` 工具进行技术选型**，禁止仅用文字表格让用户口头确认。

### 问题前缀强制规则（强制）

**所有选型问题的 `header`（标题）必须以"前端-"或"后端-"前缀开头**，禁止使用无前缀的标题（如"状态管理"、"缓存方案"），避免用户混淆前后端层级。

正确示例：`"前端-状态管理"`、`"后端-缓存方案"`、`"前端-UI 组件库"`、`"后端-ORM/数据访问"`
错误示例：`"状态管理"`、`"缓存方案"`、`"UI 组件库"`、`"ORM/数据访问"`

### 前后端分离选型规则（强制）

**前端和后端的逐层选型必须分阶段进行，禁止在同一轮问题中混合前端和后端层级。**

- 必须先完整选完前端所有基础层级和前端收尾配套推荐，再开始后端选型
- 每轮问题只能属于同一端（全前端或全后端），且每轮只能有一个问题
- 前端基础层级完成后，必须先完成“前端-配套插件推荐”；用户确认后，明确告知用户"前端技术栈与配套插件已确认完毕，接下来进入后端技术选型"，再开始后端选型

### 选型分四阶段（阶段内逐次单问）

### 阶段一：技术栈核心选择（跨端逐次单问）

按顺序询问前端主框架、后端运行时、后端开发语言、数据库、部署方案等核心选型。每轮只能展示一个问题；用户确认后必须重新动态调研，再生成下一个问题。此阶段可在前后端全局决策之间切换，但禁止同一轮同时提问多个层级：

```
# 每轮仅允许 questions 数组包含一个问题
ask_followup_question({
  questions: [{
    question: "前端主框架？",
    header: "前端-主框架",
    options: ["由 AI 实时调研生成的候选 A", "候选 B", "候选 C"],
    multiSelect: false
  }]
})

# 用户确认后：保存结果 → 重新 web_search → 兼容性评估 → 生成下一轮单个问题
```

### 阶段二：前端逐层拓展选择（仅前端，联动勾选）

根据阶段一的前端主框架选择结果，**逐层**展示前端兼容的候选方案，每层都让用户选择。**此阶段所有问题只包含前端层级，禁止混入后端层级。**

每完成一个前端选择，立即执行一次联动循环：

1. 保存用户选择并更新累计上下文
2. 动态搜索与全部已选项兼容的下一层框架、扩展和插件
3. 检查刚选技术是否触发高价值配套项；若触发，可优先插入一个独立的可选插件问题
4. 只向用户提出一个下一步问题，等待确认后再继续

例如用户选择 Pinia 后，不直接进入预设的路由问题；AI 先实时调研 Pinia 当前常用扩展及兼容性，可提出“前端-Pinia 配套插件”单个多选问题，候选可包含实时验证后的 `pinia-plugin-persistedstate` 和“无”。

前端所有基础层级选完后，必须执行一次收尾配套推荐：

1. 基于完整前端选择重新执行 `web_search`，不得复用某一层的旧搜索结果
2. 动态筛选约 5 个与已选技术兼容、对当前业务有明确价值的插件或开发工具；不足 5 个时宁缺毋滥
3. 每个候选必须是独立插件或工具，不得把多个插件绑定为一个选项
4. 使用 `multiSelect: true` 的“前端-配套插件推荐”问题展示，并提供“无（暂不需要）”；若交互工具单题候选上限不足以容纳约 5 个插件与“无”，则按运行时/工程集成、开发体验等职责拆成连续 2 个收尾问题，仍属于同一阶段
5. 所有收尾问题都确认后，才明确告知：

> 前端技术栈与配套插件已确认完毕。接下来进入后端技术选型。

### 阶段三：后端逐层拓展选择（仅后端，联动勾选）

根据阶段一的后端运行时与开发语言选择结果，**逐层**展示后端兼容的候选方案，每层都让用户选择。**此阶段所有问题只包含后端层级，禁止混入前端层级。**

后端同样执行“选择一次、调研一次、只问一次”的循环。例如选择 NestJS 后，AI Agent 必须实时调研当前 NestJS 生态、项目需求和已选认证/API/部署方案，再决定下一问是常规层级还是 `@nestjs/swagger`、`@nestjs/throttler` 等配套插件问题；插件候选不得写死，非必要时必须包含“无”。后端所有基础层级完成后，必须按前端相同规则执行一次约 5 项的“后端-配套插件推荐”；用户确认后才能进入阶段四。

**关键规则：**
- 每轮只能提出一个勾选问题；框架或库选择通常动态生成 5-8 个候选，插件或扩展选择通常生成 3-5 个候选
- 每个选项标注"推荐"标签和一句话理由，但候选必须来自本轮实时调研
- **所有问题 header 必须带"前端-"或"后端-"前缀**（阶段一的全局决策除外）
- **同一轮问题不得混合前端和后端层级**（阶段一可在不同轮次处理全局决策）
- **每次选择后必须按「0.5 多选兼容评估协议」重新评估 multiSelect 值**（可多选层级用 `true`，互斥层级用 `false`）
- 已选框架覆盖的层级，提供"使用内置"和独立方案等候选，仍需用户确认
- 配套插件以独立选项多选形式展示；非必要插件问题必须包含“无（暂不需要）”
- 用户多选后，AI Agent 必须在 Core 层为每个方案独立封装并统一对外接口

## 7.3 能力感知与冗余提示（强制）

**AI Agent 必须感知已选框架自带的能力，在后续层级标注"已覆盖"提示。**

核心规则：

1. **能力覆盖检测** — 用户选择某框架后，AI Agent 检查该框架是否已覆盖后续某层的能力
2. **覆盖提示** — 若已覆盖，该层仍需询问用户，但将"使用内置"作为推荐项标注"已覆盖"
3. **升级提示** — 若用户需求超出内置能力，推荐独立方案并说明"内置能力不足时选择"
4. **多选插件** — 配套插件以多选勾选形式展示，用户按需勾选

常见能力覆盖关系（完整矩阵见 `references/tech-stack-guide.md` 第 2.3 节）：

| 已选框架 | 覆盖的层级 | 推荐策略 |
|----------|-----------|----------|
| Element Plus (Vue) | L9 表单验证 | 推荐"使用内置验证"，但仍需用户确认 |
| Ant Design (React) | L9 表单验证 | 推荐"使用内置验证"，但仍需用户确认 |
| NestJS | L8 认证 | 推荐 `@nestjs/passport`，但仍需用户确认 |
| Vue Router | L8 路由 | 推荐 Vue Router，但仍需用户确认 |
| SvelteKit | L8 路由 + L3 构建 | 推荐 SvelteKit 内置，但仍需用户确认 |
| Next.js | L3 构建 + L8 路由 | 推荐 Next.js 内置，但仍需用户确认 |

## 7.4 分层联动规则

**前序选择影响后序可选项和推荐，但不代替用户选择。**

- 选 Vue → L4 展示 Vue 生态组件库候选，L7 推荐 Pinia，L8 推荐 Vue Router — 均需用户确认
- 选 React → L4 展示 React 生态组件库候选，L7 推荐 Zustand/Redux Toolkit，L8 推荐 React Router — 均需用户确认
- 选 Svelte → L4 展示 Svelte 生态组件库候选，L7 推荐 Svelte Stores，L8 推荐 SvelteKit 路由 — 均需用户确认
- 选 Node.js → L4 展示 Node 生态 ORM 候选，L9 推荐 Pino — 均需用户确认
- 选 Java → L4 展示 Java 生态 ORM 候选，L9 推荐 Logback — 均需用户确认
- 选 Go → L4 展示 Go 生态 ORM 候选，L9 推荐 Zap — 均需用户确认

**关键：** "推荐"不等于"自动选择"。每一层都必须让用户勾选确认。

## 7.5 选型层级与顺序（强制）

**选型阶段只用于导航：阶段一（核心选择）→ 阶段二（前端基础层级 → 前端配套插件收尾）→ 阶段三（后端基础层级 → 后端配套插件收尾）→ 阶段四（跨端关注点）。阶段内必须逐次单问；插件或扩展既可在某次选择后动态插入，也必须在每一端基础层级结束时执行一次收尾推荐。**

### 阶段一：核心选择（跨端，可混合）

全局决策项，可以在不同轮次按需询问：
- 前端主框架、后端运行时、后端开发语言、数据库、部署方案

后端运行时与开发语言必须作为两个独立问题展示。例如选择 `Node.js` 后，后端开发语言仍由用户在 `TypeScript`、`JavaScript` 等兼容候选中独立选择。

### 阶段二：前端全部层级（按顺序，禁止混入后端）

**前端-主框架** → **前端-开发语言** → **前端-构建工具** → **前端-UI 组件库** → **前端-CSS 方案** → **前端-网络请求库** → **前端-状态管理** → **前端-路由** → **前端-表单验证**（可能被 UI 库覆盖，但仍需确认）→ **前端-测试框架** → **前端-代码质量工具** → **前端-国际化**（按需）

### 阶段三：后端全部层级（按顺序，禁止混入前端）

**后端-运行时**（阶段一已选）→ **后端-开发语言**（阶段一已选）→ **后端-框架** → **后端-API 规范** → **后端-ORM/数据访问** → **后端-数据库**（阶段一已选）→ **后端-缓存** → **后端-消息队列** → **后端-认证** → **后端-日志** → **后端-测试框架** → **后端-文件存储**（按需）→ **后端-定时任务**（按需）

### 阶段四：跨端关注点

**前后端选型全部完成后**，引导选择 CI/CD 方案和错误监控/APM 方案。

## 7.5-A 选型进度追踪（强制）

选型过程中，AI Agent 必须在每轮用户确认后输出进度摘要，让用户随时了解已选/未选/明确跳过的状态：

```
## 选型进度 [3/12 前端层级已完成]
✅ 前端-主框架: Vue
✅ 前端-开发语言: TypeScript
✅ 前端-构建工具: Vite
⬜ 前端-UI 组件库: 待选
⬜ 前端-CSS 方案: 待选
⬜ 前端-网络请求库: 待选
... (剩余层级)
```

**规则：**
- 每轮用户确认后立即输出进度摘要
- 已选层级标注 ✅ 和选型结果
- 未选层级标注 ⬜
- 被跳过的层级（如纯后端项目跳过前端）标注 ⏭️ 和"本项目不需要"
- 所有层级选完后进入选型结果汇总

## 7.5-B 选型结果汇总（强制）

所有选型层级完成后，AI Agent **必须**输出技术栈汇总表，并自动填充到 `.agent/architecture.md` 的技术栈清单表格中：

```
## 技术栈选型结果汇总

| 层 | 选型 | 版本 | 选择理由 |
|----|------|------|----------|
| 前端-主框架 | Vue | 3.x（实时查询） | ... |
| 前端-开发语言 | TypeScript | - | ... |
| 前端-构建工具 | Vite | x.x（实时查询） | ... |
| 后端-框架 | NestJS | x.x（实时查询） | ... |
| 后端-数据库 | PostgreSQL | x.x（实时查询） | ... |
| ... | ... | ... | ... |

版本号必须实时查询（按 references/tech-stack-guide.md 0.1 协议），禁止沿用历史版本。
```

**后续动作：**
1. 用户确认汇总表
2. 按项目级别生成初始化计划
3. 先从 `templates/` 创建所需目录和模板文件（包括 `.agent/architecture.md`）
4. 将已确认的技术栈、版本、理由和日期写入架构说明
5. 仅 L 级或高风险决策生成 ADR-001，统一保存到根目录 `docs/adr/`
6. 安装依赖并执行初始化验收：配置检查、启动检查、测试检查、构建检查
7. 验收通过后进入项目开发；失败则保留诊断结果并允许从失败步骤恢复

## 7.5-C 选型变更流程

用户在选型过程中或选型完成后可以变更已选方案：

1. **用户提出变更**（如"前端框架从 Vue 换成 React"）
2. **AI Agent 评估影响范围**：
   - 受影响的后续层级（UI 组件库、状态管理、路由等）
   - 兼容性检查（与新选框架的兼容性）
   - 已选但不再兼容的层级清单
3. **AI Agent 提示影响并请求确认**：
   - 列出需要重新选择的层级
   - 列出将自动失效的已选方案
4. **用户确认后**：
   - 更新已选方案
   - 重新进行受影响层级的选型
   - 更新进度追踪和结果汇总

## 7.6 交互规则按模式调整

- **引导模式**：每轮一个勾选问题，候选 3-5 项，标注"推荐"和一句人话解释
- **产品模式**：每轮根据最新选择动态生成下一问题，用户逐项确认或微调
- **专家模式**：每轮一个问题，候选数量由实时调研结果决定；推荐项标注"推荐"，用户逐层选择
- **任何模式**：动态版本解析（`npm view <pkg> version` / Maven Central / Go Module Proxy / PyPI），禁止沿用历史版本号
- **任何模式**：用户每确认一个选项后，下一次提问前必须基于全部累计上下文重新执行 `web_search`，文档表格只能作为检索线索，不能直接作为最终候选
- **任何模式**：每次只提出一个问题，动态生成 3-5 个独立候选；非必要层级和插件问题必须提供“无（暂不需要）”
- **任何模式**：每次重新评估当前层级的 `multiSelect` 值，可多选层级用 `true`，互斥层级用 `false`
- **任何模式**：禁止自动填充、自动锁定、静默跳过层级；可选层级必须由用户通过候选中的“无（暂不需要）”明确确认
- **任何模式**：所有问题 header 必须带"前端-"或"后端-"前缀（阶段一全局决策除外）
- **任何模式**：同一轮问题禁止混合前端和后端层级（阶段一全局决策除外），且每轮只能包含一个问题；前端全部选完后再选后端

详细候选方案、能力覆盖矩阵、兼容性矩阵、联动规则、子插件推荐见 `references/tech-stack-guide.md`。

# 八、项目整体架构

L 级项目统一采用：**Core + Business Module + Plugin + Infrastructure + Documentation + Test**

```
project
├── core              # 核心基础能力（前后端结构不同，见 references）
├── modules           # 业务模块（DDD）
├── plugins           # 插件扩展
├── infrastructure    # 基础设施层
├── config            # 全局配置
├── docs              # 文档（含 ADR）
├── tests             # 测试
└── README.md
```

关键规范（详细见 `references/architecture-design.md`）：

- **Core**：稳定、通用、低变化、高复用；禁止包含业务代码；前端 Core 与后端 Core 结构不同
- **业务模块**：后端 DDD 四层 `domain / application / infrastructure / interfaces`；前端采用功能导向结构 `api / components / composables / stores / views`（详见 architecture-design.md 第 6 节）
- **模块通信**：后端同进程直接调用 Application Service、跨模块事件驱动；前端 Props/Events + Core Store 共享（详见 architecture-design.md 第 7 节）
- **复用规则**：新增功能前按序检查 Core → 已有模块 → Plugins，禁止重复造轮子
- **ADR**：所有重要技术决策记录到 `docs/adr/`，格式见 `references/architecture-design.md` 第 5 节
- **Monorepo**：前后端同仓时采用 `packages/shared + client + server` 结构，pnpm workspaces + Turborepo（详见 architecture-design.md 第 11 节）

# 九、AI 开发生命周期

项目任务必须根据规模与风险执行对应生命周期：

- **S 级低风险**：理解 → 实现 → 验证 → 总结
- **M 级低风险**：理解 → 分析 → 设计 → 实现 → 验证 → 总结
- **L 级或任意高风险**：必须完整执行六阶段，并增加安全、发布和回滚门禁

详细步骤见 `references/dev-lifecycle.md`。任何被裁剪的阶段都必须在总结中说明原因，不能静默跳过。

# 十、关键红线（各模式通用）

- **测试**：新功能必须有单元测试 + 集成测试，覆盖正常/异常/边界
- **安全**：禁止硬编码密码、提交 API Key、暴露数据库账号、输出敏感日志；必须环境变量管理、权限控制、输入验证、日志脱敏
- **Core 修改**：必须说明修改原因、影响范围、兼容方案、迁移方案
- **删除代码**：先检查引用关系、历史兼容、API 影响
- **README**：项目必须包含 README.md（8 要素见 `references/dev-lifecycle.md` 第 6 节）
